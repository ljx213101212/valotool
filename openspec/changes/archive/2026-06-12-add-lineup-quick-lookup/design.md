# Design — 点位速查 MVP

## 1. 总体结构：与复盘 Web 应用并存的双形态

```text
valotool（pnpm workspace）
  ├─ （现有根应用）Web 复盘：Vite + React，构建方式不变
  ├─ apps/lineup/            Taro 4（React 语法、TS），构建目标 weapp + h5
  └─ packages/lineup-content/ 内容 schema + 元数据注册表 + 点位 JSON + 校验脚本
```

- 选 Taro 而非「先 H5 后小程序」：核心受众在微信内，一套代码同时产出小程序与 H5，
  避免 H5 验证后重写；Taro 用 React 语法，与现有技术栈认知一致。
- 现有根应用暂不迁入 `apps/`，降低本变更的爆炸半径；workspace 化只增不改。

## 2. 内容模型关键决策

### 2.1 v1 不做后台，内容即代码

点位内容以 git 管理的 JSON 文件生产，配 zod schema 校验脚本（CI/pre-commit 可跑）。
理由：MVP 阶段内容由自己生产，瓶颈在「拍图 + 标注」而非「录入」；后台管理平台（含图上
标注工具）等内容生产流程稳定后再立独立变更。

### 2.2 三图卡是内容的最小完整单元

每条点位的 `images` 按角色固定为最多三张：

| role | 内容 | 要求 |
|---|---|---|
| `stand` | 站哪 | 带环境参照物，能自我定位 |
| `aim` | 瞄哪 | 准星对齐点放大图 |
| `effect` | 落点效果 | 技能生效后的结果 |

配一行 `technique`（站立/跳投/长按跳投/跑跳投等枚举）与可选时机说明。允许 1–3 张
（如原地脚下技能可只有 1 张），但 role 语义固定，保证全库视觉一致性。

### 2.3 版本有效性是一等公民

每条点位必填 `verifiedPatch`（如 `"10.11"`）与 `status: verified | stale | draft`。
地图改版时人工把该图全部点位批量置 `stale`，前端对 stale 显示「⚠️ 待验证」而非隐藏。
信任感来自「敢标过期」，不是假装全部有效。

### 2.4 难度分档驱动策展

`tier: must-learn | advanced | flashy`（必学/进阶/花活）。「必学」每个
图×英雄×阵营组合内目标 ≤5 条，是默认入口「急救包」的数据来源；全量列表按 tier 分组。

### 2.5 检索元数据内置于注册表

地图/英雄注册表每条含：官方中文名、英文名、拼音全拼、拼音首字母、社区别名数组
（火男=炼狱、EZ 等）。结构化搜索「亚海猎枭防B」即对封闭词表做分段模糊匹配——这也是
v1.5 语音输入（ASR 结果纠错）的同一套基础设施。

## 3. 速查体验关键决策

- **路径**：首页大按钮 →（九宫格）地图 →（网格）英雄 → 点位列表（默认「必学」tab +
  攻/防、站点筛选）→ 点位卡（左右滑动翻图）。目标：冷启动 ≤4 次点击到首图。
- **记住用户**：本地存储最近查询与常用英雄，二次打开首页直接展示快捷入口（两次点击到答案）。
- **图片策略**：WebP 多尺寸（列表缩略 / 卡片大图），选定地图后预取该图必学点位首图。
  v1 图床用腾讯云 COS + CDN（国内速度），URL 存于内容 JSON。
- **收藏**：v1 纯本地（小程序 storage / localStorage），无账号体系。

## 4. 合规与上架

- 小程序注册**工具/信息查询类目**，严禁游戏类目（需版号资质）。
- 不使用官方 logo 作小程序头像/名称；素材为自制游戏截图加自制标注层。
- 等待 deep-research 合规调研结论，如有先例风险再调整素材策略。

## 5. 与复盘主线的关系

- 共享层目前只有「地图/英雄元数据」概念上重叠；实现时若能从 `src/` 提取常量则提取，
  不强行抽象。
- 阶段 2（复盘→点位推荐）依赖本内容模型的 `map+site+side+purpose` 维度，schema 设计
  已预留，不在本变更实现。
